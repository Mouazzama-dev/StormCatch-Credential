# Monthly progress report

## Stormcatch robot gate-authorisation pilot

**Period:** 15 October to 15 November 2026
**Prepared by:** Mouazzama Binte Umer
**Area:** credential-lifecycle (issuance, holding, verification, interaction points)

## Summary

This month closed out the Phase 3 integration with the two partner platforms, put real trust behind the robot's identity, set up automated test reporting for every component, and built the first version of the pilot's pickup and drop-off interaction points. The credential-lifecycle services now run end to end against the real policy engine, and the pilot's delivery flow works from the pharmacy counter through to the ward handover.

## 1. Phase 3 integration and trust anchoring

The three platforms (the certificate platform, the credential lifecycle, and the policy engine) now run together in one flow. A real birth certificate issued by the certificate platform is accepted by the robot holder, the identity it carries becomes the robot's identity in the policy engine, and the facility deny list keys on that real serial, so a recalled unit is refused even with otherwise valid authorisation.

To make that trust real rather than a stopgap, the decision-service was given X.509 root-chain anchoring. A birth certificate is now trusted when its certificate chains up to a trusted root, instead of pinning one exact signing certificate. This means a rotated signing certificate keeps working without re-pinning, and a certificate from any other root is refused. The change is backward compatible, so the existing fingerprint and DID anchors still work alongside it, and it is covered by unit tests.

## 2. Automated test reporting

A test report is now produced for each component, so the health of every part is visible and easy to hand over.

- A per-component report tool writes a standard JUnit report for each component, using the built-in test runner with no extra dependency.
- A continuous-integration workflow regenerates the self-contained reports automatically on every change, so a report is never stale.
- The tests are organised into three levels: the self-contained logic that runs automatically (Level 1), the service contracts that need the live services (Level 2), and the full end-to-end run (Level 3).
- Every component suite and the end-to-end flow pass. The latest run records 79 passing tests and one graceful skip (a single gate test that needs a live Paradym session), with nothing failing.
- A test report document and a reusable report template were produced so the rest of the team can report their own modules in the same shape.

## 3. Interaction points: pickup and drop-off

The pilot's two manned interaction points were implemented: the pharmacy pickup and the ward drop-off.

- At pickup the robot is authorised at the counter through the policy engine, and the payload it will carry is issued as a signed token (an ES256 JWT) with a unique id, designed behind a backend interface so it can be replaced by a verifiable credential once the platform is ready.
- The robot carries the token, and each transit gate can check it (valid, not expired, not revoked) alongside the robot's identity.
- At drop-off the token is checked and the robot is authorised again. On receipt, the token is revoked. Because only the issuer may revoke, the drop-off asks the issuer to revoke over a message channel, the issuer blacklists the token's id, and that revocation is announced as a retained message so every point stays in sync. A token that has been used is then refused if presented again.
- A central token issuer, a task store that plans deliveries ahead, and an activity log were added, and the interaction points were tested against the real policy engine and a message broker.

## 4. Supporting work

- A development stack launcher brings up all the services with a single command, which makes local testing and demos repeatable.
- A user-facing application was built for the pilot, with simple desks for the people at each point, the delivery stories shown on a floor plan, and a control room view.
- Access to the two pilot devices was set up, so hardware-in-the-loop testing can begin.
- The agenda and follow-ups for the partner meeting with the wallet provider were prepared, covering the verification API, the multi-level verification question, and the issuer-trust status.
